## Summary
- Tighten `query_running_vms` window from 24 h to 30 min (parameterised).
- Eliminates the race between hourly analysis and 15-min prune that caused deleted VMs (e.g. `testDME`, `hypercore-manager24`) to keep reappearing on the Concrete Right-Sizing tab.

## Why
`query_running_vms` looked at the last 24 h of `vm_inventory`. When a VM is deleted, the collector stops writing inventory records, but the *last* record from before deletion sits in that 24 h window with `vm_state == "RUNNING"`. So the analysis layer's "is this VM running?" check kept saying yes for up to 24 h after deletion. Each hourly analysis cycle re-inserted those VMs into `right_sizing` / `resize_recommendations`, then the 15-min prune loop wiped them, then the next analysis cycle put them back. Whichever one ran most recently determined what the dashboard showed.

`testDME` showing `—` for vCPU was a giveaway: `query_vm_vcpu` had already aged its data out, but `query_running_vms` still let the VM through the running filter, so `current_vcpu` ended up `NULL` while the row itself survived.

The prune loop's `query_active_vms` already uses a 30-min window on `vm_metrics` and gets this right; this PR just brings `query_running_vms` in line with the same shorter horizon. `vm_inventory` is written every slow-poll cycle (default 5 min) so 30 min is plenty of slack while still letting deleted VMs fall out before the next analysis cycle.
