# Phase 4 — Data Sharing with Foresight-Central

## What is Data Sharing?

Foresight Sentinel can push capacity conclusions to an Foresight-Central viewer operated
by your managed service provider (MSP). This lets your MSP team
review your cluster's forecast snapshots, right-sizing recommendations, and capacity projections
without requiring direct access to your HyperCore environment.

Data sharing is **opt-in** and push-only: Sentinel initiates all connections outbound from your
site to the viewer. The viewer has no inbound access to your cluster or to the InfluxDB metrics
store. Only computed conclusions are transmitted — raw metrics and credentials never leave your
environment.

---

## What Data is Shared?

| Data | Included | Notes |
|---|---|---|
| Forecast snapshots | Yes | Regression model outputs only (30d, 90d, 180d, 365d horizons) |
| Right-sizing recommendations | Yes | VM names can be anonymised — see Anonymisation section |
| Cluster health scores | Yes | Aggregated per-cluster score, no per-node breakdown |
| Capacity exhaustion projections | Yes | Projected dates at current growth rate |
| Raw InfluxDB metrics | No | Never shared; they remain on-site |
| VM workload details | No | Only aggregated recommendations are included |
| Credentials / passwords | No | HyperCore, InfluxDB, and PostgreSQL credentials stay local |
| Node-level utilisation telemetry | No | Not included in any sync payload |

## Enabling Data Sharing

You will need two pieces of information from your MSP administrator before you begin:

- **Viewer URL** — the HTTPS address of the Foresight-Central instance
  (e.g. `https://foresight-central.example.com`)
- **Enrollment Code** — a short, time-limited code generated by the admin for your tenant
  (valid for 48 hours)

### Step-by-step

**Step 1 — Obtain your enrollment code**

Contact your MSP administrator. Ask them to generate an enrollment code for
your tenant in Foresight-Central. They will provide you with:
- The viewer URL
- The enrollment code (e.g. `ENR-A3F7-X9QZ`)

The code expires 48 hours after it is generated. If it expires before you complete setup, ask
your admin to regenerate it.

**Step 2 — Open the Data Sharing panel**

Log in to the Sentinel dashboard and navigate to:

**Foresight → Data Sharing**

**Step 3 — Enter the Viewer URL**

In the **Viewer URL** field, enter the address provided by your admin. It must begin with
`https://`. Example:

```
https://foresight-central.example.com
```

Sentinel will reject a plain `http://` URL as insecure.

**Step 4 — Enter the enrollment code**

Paste the enrollment code into the **Bearer Token / Enrollment Code** field exactly as given.
Do not add spaces or quotes. Sentinel will exchange this code for a long-lived bearer token
automatically when you save — you will not need to handle the token manually.

**Step 5 — Enable sharing**

Toggle **Sharing Enabled** to the on position.

**Step 6 — Save**

Click **Save**. Sentinel stores the viewer URL and exchanges the enrollment code for a bearer
token in the background. This may take a few seconds.

If the exchange fails (e.g. the code has expired), an error banner is displayed. Ask your admin
to regenerate the enrollment code and try again.

**Step 7 — Verify connectivity**

Click **Test Push**. Sentinel sends a minimal test payload to the viewer and reports success or
failure. A successful test push confirms:
- The viewer URL is reachable from your network
- The bearer token is valid
- The viewer accepted the payload

If the test push fails, check the error message and refer to the troubleshooting section below.

**Step 8 — First automatic sync**

After a successful test push, Sentinel will sync automatically on its configured interval
(default: every **4 hours**). The first full sync may take slightly longer than subsequent ones
as Sentinel assembles the initial snapshot.

You can trigger a full sync at any time by clicking **Sync Now** in the Data Sharing panel.

## Anonymisation

The Data Sharing panel provides three independent anonymisation toggles. Enabling them replaces
identifying names with stable pseudonyms before any data leaves your site.

| Toggle | What it affects |
|---|---|
| **Anonymise VM names** | VM display names are replaced with stable pseudonyms (e.g. `vm-a3f7`, `vm-b92c`). Pseudonyms are consistent across syncs so trends remain intact. |
| **Anonymise node identifiers** | Physical node names/IDs in recommendations are replaced with pseudonyms (e.g. `node-01`, `node-02`). |
| **Anonymise cluster name** | Your cluster name is replaced with a pseudonym in all shared payloads. |

**Important:** Pseudonyms are derived deterministically from the original names using a local
key. The same VM always maps to the same pseudonym, so the viewer can track trends over time
even when anonymisation is enabled. The mapping key never leaves your site.

You can change anonymisation settings at any time. Changes take effect on the next sync. The
viewer will see the updated pseudonyms from that point forward; historical data in the viewer
retains the pseudonyms that were in use when it was pushed.

## Manual Export (.hcb File)

For environments where outbound HTTPS to the viewer is not possible (air-gapped sites, strict
firewall policies), Sentinel supports a manual export workflow.

**Exporting a snapshot:**

1. Navigate to **Foresight → Data Sharing**.
2. Click **Download Snapshot (.hcb)**.
3. Sentinel generates an AES-256 encrypted snapshot file and your browser downloads it.

**Importing into the viewer (admin task):**

Send the `.hcb` file to your MSP administrator. They import it via:

**Admin → Tenants → [your tenant] → Import .hcb**

The viewer decrypts and ingests the snapshot. The data appears in the tenant's dashboards within
a few seconds of import.

`.hcb` files are encrypted with AES-256. The encryption key is derived from your tenant's
shared secret, which is established during enrollment. A `.hcb` file produced by one tenant's
Sentinel instance cannot be imported into a different tenant's record.

## Sync Status

The **Data Sharing** panel in the Sentinel dashboard shows:

- **Last sync time** — timestamp of the most recent successful push
- **Status badge:**
  - `OK` — last push succeeded
  - `Pending` — no sync has completed yet (normal immediately after enrollment)
  - `Error` — last push failed; hover for the error message
- **Sync interval** — the configured interval between automatic syncs (default 4h)
- **Test Push** and **Sync Now** buttons for on-demand actions

If the status badge shows `Error`, check the viewer URL and bearer token are still valid, and
confirm your network allows outbound HTTPS to the viewer host. Your admin can also check the
viewer's audit log for rejected push attempts.

---

## Disabling Data Sharing

To stop sharing data:

1. Navigate to **Foresight → Data Sharing**.
2. Toggle **Sharing Enabled** to the off position.
3. Click **Save**.

Sentinel will no longer push any data. Existing data already in the viewer is not automatically
deleted — contact your admin if you need it removed.

## Troubleshooting

**Test push fails with "connection refused" or timeout**

- Confirm the Viewer URL is correct and begins with `https://`.
- Verify your network allows outbound HTTPS (TCP 443) to the viewer host.
- Ask your admin to confirm the viewer is running: `curl https://foresight-central.example.com/health`
  should return `{"status":"ok"}`.

**Test push fails with "401 Unauthorized"**

- The enrollment code may have expired before the exchange completed. Ask your admin to
  generate a new enrollment code, paste it in the Bearer Token field, and save again.
- If the exchange previously succeeded, the bearer token may have been revoked by the admin.
  Ask them to check the tenant record in the viewer.

**Sharing was working, now showing Error**

- The bearer token may have been rotated or revoked on the viewer side. Ask your admin to
  regenerate the enrollment code and re-enroll.
- Check that the viewer URL has not changed (e.g. after a domain migration).

**Anonymisation pseudonyms changed unexpectedly**

- Pseudonyms are stable as long as the local mapping key is intact. If the Sentinel container
  was rebuilt from scratch and the PostgreSQL volume was not preserved, the mapping key may have
  been regenerated. Contact your admin to reconcile historical data in the viewer.
